# Shared development persistence

The deployed persistence path is prepared but **disabled by default**. Activation is an engineer checkpoint. This guide uses the existing [Google Cloud maintenance process](google-cloud.md#pause-and-resume-releases): prevent merges/dispatches, disable delivery, drain all active and queued runs, perform the coordinated change, verify, then resume. This applies to bootstrap, Terraform configuration changes, credential rotation, database repair and manual rollback. Routine releases remain automatic after checked merges and never run Terraform.

## Bootstrap and credentials

1. The engineer creates their Neon account and a dedicated **Free** project in **aws-us-east-1**, selecting **PostgreSQL 17** (local/CI pin 17.6). Keep one development branch and one database named `tour_itinerary`. Check Free limits and connectivity; do not enable paid plans or preview branches. Neon supplies patch updates within the selected major. Administrative credentials stay with the engineer and are never given to delivery or the API.
2. Using the Neon administrative connection privately, run `backend/database/roles.sql` once. SQL-created `it_migration` and `it_runtime` have LOGIN but no superuser, role/database creation or replication privileges. Set distinct generated passwords interactively with psql `\password it_migration` and `\password it_runtime`; never paste passwords into command arguments, SQL files, issues or shell history. Create the database owned by `it_migration` (or deliberately transfer the empty default database's ownership). In that database run `backend/database/permissions.sql` with `-v database=tour_itinerary -v ON_ERROR_STOP=1`. Also run `backend/database/shared-settings.sql` with the same database variable to bound migration statements to 60 s and locks to 10 s. Check role memberships: neither login may inherit Neon admin or other privileged roles. The migration owner must own the public schema or have its USAGE/CREATE grants; runtime has CONNECT and schema USAGE only. Review the SQL before execution; do not blindly repeat CREATE ROLE against existing roles.
3. Build two URLs using those SQL-created logins, not Neon's administrative login. Runtime uses the project's **pooled** `*-pooler.*.neon.tech` hostname and `it_runtime`; migration uses the **direct** `*.neon.tech` hostname without `-pooler` and `it_migration`. Both use database `tour_itinerary` and `sslmode=verify-full`. Percent-encode credentials. The migration URL also requires `connect_timeout=10`; do not add search-path, shadow, or other query overrides. Connection mode alone does not restrict permissions.
4. With persistence still disabled, review/apply Terraform to create `api-runtime-database-url` and `api-migration-database-url` and enable Secret Manager. Terraform grants Secret Accessor on the first secret only to `api-runtime` and on the second only to `github-delivery`. Existing Service Account User lets delivery deploy the runtime identity; it is not a direct runtime-secret access grant. Inspect inherited IAM too. Terraform never manages secret versions or values. No project-wide Secret Accessor, database admin credentials, GitHub database secrets or PR credentials are needed.
5. Enter each URL **directly into its individual Google Secret Manager secret** using the engineer console or `gcloud secrets versions add SECRET --data-file=- --project="$PROJECT_ID"` with private stdin from a password manager. Do not echo, log, save to a Terraform input/plan/state, or upload the URL. Record only the returned positive numeric version identifiers. Never use `latest` or a version alias. Keep the secrets enabled and check access policies privately.

## Activation

There is one gate: private reviewed Terraform input `enable_persistence = true`. Set `runtime_database_secret_version` and `migration_database_secret_version` to the explicit numeric versions. No GitHub activation variable exists. Terraform places the mode and migration version in service labels and pins `DATABASE_URL` to the runtime secret version in the revision configuration. The migration URL is never placed in Cloud Run. Disabled services receive no database environment value; disabled releases neither fetch database secrets nor install/run migration tools.

During the maintenance window, review compatibility of every committed migration and fixture change with the currently serving **and retained rollback** revisions. Migrations must be additive/expand-then-contract as needed. Incompatible changes require human planning. The current health-only revision ignores database configuration and is compatible with the fixture migration. Apply the reviewed configuration; verify that the expected image/commit, ordinary settings and explicit traffic are preserved. Terraform may create a new revision for the configuration; identify that revision, verify independent health and pin traffic deliberately if required before resuming.

Read service metadata labels `persistence-mode=enabled` and `migration-secret-version=N` and the template's runtime `DATABASE_URL` secret reference back privately. Inconsistent configuration fails delivery rather than falling back to health-only. Legacy services with neither gate labels nor a runtime database setting remain health-only before the preparation apply. Record the non-secret references and checked image/commit on the issue. Re-enable delivery and dispatch a normal release from successful CI for current merged `main`. Even if that commit is already serving, activated delivery must run migrations and explicit seeding before its no-op health check. A stale release skips before any secret access or DB mutation.

The serialized path is: checked image verification/publication → capture previous revision/commit/digest and health → eligibility recheck → fetch selected migration version into child-process memory → locked `prisma migrate deploy` → explicit fixture seed → candidate deployment/health → promotion/normal health. No image rebuild, migration at startup or new routine approval gate is added. Failure at migration or seed stops before candidate rollout and leaves existing traffic alone. Publish-only never touches the database.

## Limits and verification

The lazy runtime provider uses max **2** connections per instance, a **5 s** acquisition timeout, **5 s** statement timeout, **6 s** query timeout and **10 s** idle timeout, with no application retries. At the configured service maximum of two instances the steady-state budget is four runtime connections; retain headroom for overlapping revisions during deployment and traffic rollback. Cloud Run's instance cap is not an exact database connection ceiling. Runtime HTTP startup and `/health` are independent of PostgreSQL, including pre-publication image tests without secrets.

The direct migration connection uses `connect_timeout=10`; the migration command's whole process group is bounded to **120 s** (including Prisma's advisory-lock handling), with role defaults of **60 s** per statement and **10 s** per lock wait with no automatic retries. Seed uses **10 s** connect, **5 s** server statement and **6 s** query timeouts; its subprocess is also bounded to 120 s. These tolerate Neon wake-up while bounding delivery failures. Inspect Neon connection/storage/compute/transfer quotas if unavailable; do not upgrade plans or raise caps automatically.

After activation, privately verify migration history, canonical fixture `Infrastructure probe ready.`, and role grants using the separate logins. As runtime, SELECT must work; INSERT/UPDATE/DELETE, CREATE TABLE/SCHEMA and ALTER/DROP must be denied. Keep denial experiments in isolated local/CI databases; for shared development inspect privileges instead of injecting mutations/outages. Local/CI use the same committed migration and seed with realistic roles. A health-only release proves HTTP delivery, not a deployed GraphQL database read.

## Failure inspection and recovery

Release summaries report mode, explicit non-secret secret references, eligibility, migration/seed outcomes, captured previous revision, final traffic and recovery. Secret retrieval, migration and seed failures are sanitized; connection strings and raw database/Prisma diagnostics are not published. Preserve private diagnostics with the engineer rather than copying secrets into workflow output.

On migration/seed failure or timeout, leave the workflow failed and stop rollout. **Do not assume no SQL ran.** Pause and drain releases, inspect Neon availability/quotas/connectivity, selected secret versions and grants. Using the direct migration login privately, inspect `prisma migrate status`, `_prisma_migrations` (including failed/unfinished rows) and actual schema/fixture state. Compare with reviewed SQL. A timeout can leave a partial migration; a failed seed may follow fully applied migrations.

The engineer deliberately completes or repairs partial changes, records reproducible repair in reviewed source/history and reconciles history only when understood. `prisma migrate resolve --applied NAME` or `--rolled-back NAME` changes migration records; it **does not undo SQL**. Follow [Prisma recovery guidance](https://www.prisma.io/docs/orm/prisma-migrate/workflows/patching-and-hotfixing). No shared reset, history deletion, destructive schema rollback or automatic repair is allowed. Never disable activation or silently skip migrations to bypass a failure. Resume/retry only from current checked main when safe.

If migration/seed succeeds but candidate or promotion fails, leave the schema and canonical fixture in place. Delivery restores/preserves only application traffic and verifies the captured previous commit; it does not undo migrations or repair a database outage. Retained revisions must continue working with the migrated state. Inspect actual service state after ambiguous CLI failures using the Google Cloud recovery guide.

## Rotation and checkpoint evidence

Pause/drain releases. Rotate one role at a time using the engineer's private admin connection and password manager, preserving restricted grants; account for existing pooled sessions and rollback revisions pinned to old runtime versions. Add a new version directly to the appropriate secret, update its explicit Terraform reference, review/apply, and verify a current checked release and runtime privileges before disabling old versions. Do not delete an old runtime version while a retained rollback revision still requires it: retain a usable credential/version or replace and verify the rollback revision deliberately. With in-place password rotation, old URLs stop authenticating even if their secret versions remain enabled; plan a maintenance outage or a separately reviewed overlapping-role transition rather than claiming automatic rollback compatibility. Do not grant routine identities administrative privileges for rotation.

The activation checkpoint records checked commit/image, selected version references, health-only/activated release evidence, migration and seed success, grants, actual traffic and manual recovery readiness. Safe failure-path verification runs against the CLI's isolated external-command simulator and disposable PostgreSQL, never by interrupting shared Neon or mutating shared fixture/schema. Exercise disabled delivery, migration failure, seed failure, stale release, application rollback with schema retained, and first activation on an already-serving commit before declaring preparation verified. Live bootstrap/activation evidence belongs on its own issue.
