# API foundation compatibility and hosting fact sheet

Investigated 2026-10-28 for [Verify the API foundation toolchain and hosting constraints](https://github.com/zrm20/tour-itinerary/issues/2), part of [Plan the first deployed API infrastructure slice](https://github.com/zrm20/tour-itinerary/issues/1). This is a research asset on a throwaway branch, not an accepted implementation decision. No application was built, dependencies installed, services provisioned, or runtime compatibility tested.

## Findings that affect the plan

1. **Pin a compatible toolchain explicitly.** Current Nest documentation describes Nest 12, GraphQL/Apollo integration 14, Apollo Server 5, and Express 5. Older scaffolding tutorials can select incompatible integration packages. [Nest migration guide](https://docs.nestjs.com/migration-guide), [GraphQL installation](https://docs.nestjs.com/graphql/quick-start).
2. **Prisma has an important release transition.** Prisma 8 is currently a release candidate and the default CLI installation has moved to it. Prisma 7 remains supported; it retains the schema, generation, and migration workflow assumed by this repo. Explicitly installing `prisma@7` avoids accidentally mixing two different APIs. Adopting Prisma 8 would be a separate human choice. [Prisma release status](https://www.prisma.io/docs/orm/release-status).
3. **Treat the database probe separately from process health.** Cloud Run can use an independent HTTP health endpoint. Its platform probes and a successful deployment do not themselves prove a GraphQL operation can read a fixture from Neon. [Cloud Run health checks](https://docs.cloud.google.com/run/docs/configuring/healthchecks).

## Schema and build requirements

- Schema-first Nest uses `.graphql` files through `typePaths`. `GraphQLDefinitionsFactory` supports a separate type-generation script; startup-only generation is optional. For this repo's pre-build checks, generating before type checking is a plausible choice. This is an inference from the documented standalone generation facility. [Nest schema-first configuration](https://docs.nestjs.com/graphql/quick-start).
- The compiled container must contain the SDL files at the paths used by the deployed process. Nest CLI supports copying non-TypeScript assets; verify the built image rather than relying on source-tree execution. [Nest assets configuration](https://docs.nestjs.com/cli/monorepo#assets).
- Prisma 7 requires a driver adapter, an explicit generated-client output, and CLI connection configuration in `prisma.config.ts`; environment loading must be explicit. A normal Node PostgreSQL adapter such as `@prisma/adapter-pg` is an option for both local PostgreSQL and Neon. Use the generated-client import path. Its underlying driver owns pooling and timeout defaults; do not copy old Prisma 6 URL tuning uncritically. [Prisma v7 upgrade guide](https://www.prisma.io/docs/guides/upgrade-prisma-orm/v7), [driver adapters](https://www.prisma.io/docs/orm/v7/core-concepts/supported-databases/database-drivers).
- Run Prisma generation and fixture seeding explicitly: v7 migration commands no longer do either automatically. Seeding is a configured `prisma db seed` command, which can establish the non-sensitive probe fixture. [Prisma v7 upgrade guide](https://www.prisma.io/docs/guides/upgrade-prisma-orm/v7), [seeding](https://www.prisma.io/docs/orm/v7/prisma-migrate/workflows/seeding).
- Use Nest testing utilities with Vitest and keep a separate type check: transformation alone does not establish type correctness. A meaningful foundation test must exercise Nest wiring and the HTTP/GraphQL route, followed by a real isolated PostgreSQL read once persistence exists. This is a testing recommendation, not a newly accepted contract. [Nest Vitest recipe](https://docs.nestjs.com/recipes/swc).

## Cloud Run and delivery facts

- Build a Linux image including `linux/amd64`; ingress must bind **`0.0.0.0:$PORT`**, not localhost. Cloud Run supplies `PORT` (default 8080) and terminates TLS. The writable container filesystem is ephemeral, so PostgreSQL data cannot live there. [Container runtime contract](https://docs.cloud.google.com/run/docs/container-contract).
- Cloud Run supplies a TCP startup probe by default. An explicit HTTP startup/liveness probe uses HTTP/1 GET and regards 2xx/3xx as success. Liveness failure restarts an instance; readiness failure stops new routing without killing it. The map's independent process health should therefore avoid restarting healthy processes for a shared database outage. The last sentence is a recommendation from these semantics. [Health checks](https://docs.cloud.google.com/run/docs/configuring/healthchecks).
- Minimum instances default to zero. Request-based billing with a zero minimum has no idle-instance charges; cold startup remains possible. Supporting services and active work can still cost money. [Minimum instances and billing](https://docs.cloud.google.com/run/docs/configuring/min-instances).
- Container deployment creates revisions. Cloud Run supports no-traffic tagged revisions, direct smoke testing, traffic promotion, and routing back to an older revision. **Inference:** routing rollback cannot undo a database migration; schema compatibility and migration recovery need their own contract. [Revision rollout/rollback](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration).
- Container deployment's documented roles are Cloud Run Developer, Service Account User on the runtime identity, and Artifact Registry Reader. Creating/updating IAM or other bootstrap work may require more. Google’s deploy action README shows broader Cloud Run Admin permissions; select permissions for the chosen operations rather than copying them wholesale. [Deployment roles](https://docs.cloud.google.com/run/docs/deploying), [action authorization](https://github.com/google-github-actions/deploy-cloudrun#authorization).
- Artifact Registry requires an existing repository, registry authentication, and Writer permissions for a push. Choose explicitly between building in GitHub Actions and using Cloud Build; deploying an already-built image does not inherently require Cloud Build. [Registry push prerequisites](https://docs.cloud.google.com/artifact-registry/docs/docker/pushing-and-pulling), [container deployment](https://docs.cloud.google.com/run/docs/deploying).
- Google's `auth@v3` supports direct Workload Identity Federation, federation through a service account, and JSON keys; federation avoids storing a long-lived key. It needs checkout first, a Node-24-capable runner, and GitHub `id-token: write`. Restrict the identity provider to the intended repository/ref; exclude generated `gha-creds-*.json` from the container/build context. Credentials are short-lived, so authenticate near the authenticated steps. [Official auth action](https://github.com/google-github-actions/auth).
- Cloud Run can reference Secret Manager via environment variables or mounted files. The runtime identity needs Secret Accessor; Google recommends version-pinning secrets used as environment variables. Configuration changes create new revisions. [Secrets configuration](https://docs.cloud.google.com/run/docs/configuring/services/secrets).
- Newly deployed services are private by default. The deployment action preserves an existing public/private IAM setting and recommends managing that choice separately. This affects who can smoke-test the infrastructure probe even though application authentication is out of scope. [Deploy action access behavior](https://github.com/google-github-actions/deploy-cloudrun#allowing-unauthenticated-requests).

No account/project/billing/API/IAM configuration was inspected or provisioned. Exact prerequisite ownership and the environment/region remain open.

## PostgreSQL, migrations, and isolation

- Neon documents pooled runtime connections and direct connections for schema operations. Its pooler uses transaction mode, so session settings and session advisory locks are unsuitable there. A conservative option is a pooled runtime URL and a separate direct migration URL, selected in `prisma.config.ts`. [Neon Prisma guide](https://neon.com/docs/guides/prisma), [pooling restrictions](https://neon.com/docs/connect/connection-pooling).
- For Prisma 7, use `migrate dev` to author migrations in development, and `migrate deploy` to apply committed migrations in CI/deployed environments. Deployment does not generate the client or detect drift. Run migration deployment as an explicit controlled workflow step; running it on every autoscaled application startup is not required. [Versioned migration workflow](https://www.prisma.io/docs/orm/v7/prisma-migrate/workflows/development-and-production).
- `migrate dev` uses a shadow database; `migrate deploy` does not. Never point the shadow URL at the application database. Destructive reset belongs only to disposable development/test data. [Shadow databases](https://www.prisma.io/docs/orm/v7/prisma-migrate/understanding-prisma-migrate/shadow-database).
- GitHub Actions can run a fresh PostgreSQL service container with a readiness check on an Ubuntu runner. This offers integration isolation without production credentials or Neon API access. **Recommendation:** use a pinned PostgreSQL major locally/CI, separate databases for local versus tests, and separate per-worker databases/schemas or sequential tests where suites mutate shared fixtures. [GitHub PostgreSQL service containers](https://docs.github.com/en/actions/tutorials/use-containerized-services/create-postgresql-service-containers).
- Neon Free currently lists **100 CU-hours/project, 1 GB storage/project, 10 branches/project, 5 GB public transfer/project, and scale-to-zero after five minutes**. These are research-date allowances, not permanent promises. A sleeping database plus a cold API can affect the first probe request. [Neon plan limits](https://neon.com/docs/introduction/plans).
- Region placement must consider both providers. Neon has a defined region catalog; pick a nearby compatible Cloud Run location and measure the real network read. **Inference:** cross-provider database traffic introduces network latency and potentially billed transfer; a Neon free allowance does not cap the whole Google Cloud bill. [Neon regions](https://neon.com/docs/introduction/regions), [Neon transfer limits](https://neon.com/docs/introduction/plans), [Cloud Run billing](https://docs.cloud.google.com/run/docs/configuring/min-instances).

## Human decisions still open

- Accept a stable Prisma 7 baseline or explicitly investigate the Prisma 8 release candidate; pin the full compatible package graph at implementation time.
- Choose repository layout, package manager, generated-file ownership, local commands, and acceptance checks for each checkpoint.
- Choose initial environment count, Google/Neon project ownership and locations, provisioning method, runtime/deploy identities, public versus IAM-restricted invocation, and cost/scale limits.
- Choose the migration runner/timing, serialization and failure handling, fixture lifecycle, test isolation, and a recovery procedure that does not assume database rollback follows application rollback.
- Choose probe SDL/response/errors, evidence of a real database read, and whether the probe is retained after infrastructure bring-up.

These questions belong to the map's human decision tickets. Research establishes no authentication or application-domain implementation requirements.
